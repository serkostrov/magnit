# Хранение изображений и резервирование

## Принятое решение

Production-хранилище изображений — отдельный MinIO в том же проекте Dokploy.
Приложение обращается к нему по внутреннему S3-compatible endpoint; bucket не
публикуется напрямую в интернет. Локальный `MEDIA_STORAGE_DIR` остаётся только
fallback для разработки и тестов.

Изображения каталога не зависят от Tilda CDN. Импорт сохраняет исходный
`external_url` для аудита, а витрина использует стабильный URL приложения:

```text
/media/products/<external-id>/<content-sha256>.<ext>
```

S3 key повторяет часть после `/media/`. Благодаря этому смена MinIO, домена или
внешнего backup-провайдера не меняет URL товара и записи PostgreSQL.

## Эксплуатационные параметры

- private bucket: `site-magnit`;
- versioning включён;
- допустимые типы: JPEG, PNG, WebP и AVIF;
- максимальный размер одного файла: 15 MiB;
- максимум изображений одного товара: 20;
- timeout загрузки исходника: 20 секунд, не более четырёх загрузок одновременно;
- дубли определяются по SHA-256 и не занимают повторное место;
- секреты MinIO передаются только через окружение Dokploy;
- прямой публичный доступ к MinIO Console и S3 API закрыт.

## Резервное копирование

Копия должна храниться вне сервера Dokploy: отдельный S3-compatible bucket или
backup-host с `mc mirror`. Snapshot PostgreSQL и mirror bucket создаются одной
ночной процедурой и получают общий timestamp.

В репозитории эту процедуру выполняет `npm run backup:storage`. Команда создаёт
атомарный комплект с `postgres.dump`, `media.tar.gz` и `manifest.json`, где для
обоих артефактов записаны размер и SHA-256; результат каждого запуска
добавляется в `backup-journal.jsonl`. По умолчанию комплект пишется в
`storage/backups`, а для off-host назначения задаётся `BACKUP_STORAGE_DIR`.
Ошибка также отправляется на `BACKUP_NOTIFY_WEBHOOK_URL` (или общий
`NOTIFICATION_WEBHOOK_URL`), если webhook настроен.

- ежедневно в 03:30 по `Europe/Moscow`;
- 14 ежедневных комплектов;
- 12 еженедельных комплектов (около трёх месяцев);
- проверка результата и размера после каждого запуска;
- тестовое восстановление в отдельном окружении один раз в месяц.

Versioning MinIO защищает от случайной перезаписи между backup-запусками, но не
заменяет off-host копию. Незавершённый или непарный комплект PostgreSQL/media
не считается пригодной резервной копией.

## Восстановление

1. Развернуть чистый MinIO и восстановить bucket из выбранного комплекта.
2. Восстановить PostgreSQL snapshot с тем же timestamp.
3. Проверить количество объектов, checksum выборки и открытие изображений через
   `/media/...`.
4. Запустить smoke-тест каталога и карточки товара, затем выполнить revalidation.

Перед рабочим импортом выполняется `npm run catalog:import -- --dry-run`.
Рабочий импорт допускается после просмотра отчёта, а ошибки и конфликты
сохраняются в `import_runs`.

## Тестовый runbook восстановления

1. Создать отдельную пустую PostgreSQL-базу и выполнить
   `pg_restore --exit-on-error --no-owner -d <restore-database> <postgres.dump>`.
2. Распаковать `media.tar.gz` в отдельный каталог, не в рабочее
   `MEDIA_STORAGE_DIR`.
3. Сверить количества `products`, связей категорий, `product_images`,
   характеристик и `audit_log` с manifest/исходной базой; отдельно проверить
   SHA-256 и открытие нескольких файлов.
4. Запустить собранный standalone-сервис с `DATABASE_URL` восстановленной БД и
   `MEDIA_STORAGE_DIR` восстановленного каталога. Проверить `/`, `/catalog`,
   одну `/catalog/<slug>` и один `/media/...`; зафиксировать HTTP-коды и время
   `pg_restore`/распаковки.
5. После проверки удалить только временную restore-БД и каталог, не изменяя
   рабочие данные и backup-комплект.
