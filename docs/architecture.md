# Архитектура второго этапа

## Границы системы

Приложение остаётся одним Next.js 16 App Router Node-сервисом в режиме
`standalone`. Отдельные микросервисы и тяжёлая CMS не вводятся. Состояние
хранят PostgreSQL и MinIO внутри проекта Dokploy; браузер не обращается к ним
напрямую.

```text
публичная витрина ─┐
личный кабинет ────┼── Next.js pages / route handlers
админка ───────────┘              │
                                  ├── PostgreSQL
импорт Tilda ─ application service┤
                                  └── MinIO (S3-compatible)
```

Онлайн-оплата и личный кабинет не входят в текущую тестовую приёмку. Их будущая
реализация не должна менять источники истины: пользовательские данные и история
заказов должны храниться в PostgreSQL. МойСклад отложен и остаётся только
отключённой будущей integration boundary. Полный список границ зафиксирован в
`docs/future-stage-backlog.md`.

## Модули

| Модуль | Ответственность | Основные границы |
| --- | --- | --- |
| Каталог | Публичные товары, категории, фильтры, пагинация | `lib/catalog`, публичные страницы |
| Импорт | Разбор Tilda CSV, нормализация, отчёт, идемпотентный upsert | `scripts/import-tilda.mjs`, `import_runs` |
| Медиа | Ключи объектов, загрузка и выдача изображений | `lib/media`, `/media/*`, MinIO |
| Админка | Товары, категории, подборки, заказы и импорты | `/admin`, `/api/admin/*` |
| Заказы и лиды | Валидация, снимки цен, согласия, статусы и уведомления | `/api/orders`, `/api/forms/*` |
| Авторизация | Пользователи, серверные сессии, cookies и CSRF | `lib/security`, `admin_users`, `admin_sessions` |
| Аудит | Неизменяемый журнал административных и системных мутаций каталога | `audit_log` |
| SEO | metadata, canonical, JSON-LD, sitemap и revalidation | страницы каталога, `app/sitemap.ts` |
| Резервирование | Согласованные PostgreSQL/media backup-комплекты | `docs/storage-backup.md` |

## Источники истины

- PostgreSQL — единственный runtime-источник товарных и публикационных данных,
  категорий, заказов, лидов, пользователей, сессий, аудита и истории импортов.
- MinIO — источник бинарных объектов изображений. PostgreSQL хранит их ключи,
  публичные URL, порядок и исходные Tilda URL для аудита.
- Tilda CSV — входной snapshot импорта, но не источник витрины после apply.
- Редакторские поля из админки не перезаписываются будущей интеграцией
  МойСклад без отдельной матрицы владения полями.
- Демонстрационный массив допустим только без `DATABASE_URL` в локальной
  разработке и тестах. Настроенная, но недоступная production-БД не должна
  незаметно переключать витрину на demo-данные.
- Браузерные `localStorage` корзины и избранного — клиентский черновик, а не
  источник созданного заказа.

## Транзакционные границы

1. Миграция применяется одной транзакцией и только после успеха записывается в
   `schema_migrations`.
2. Один импортируемый товар — одна PostgreSQL-транзакция: product, категории,
   подборки, изображения и характеристики либо фиксируются вместе, либо
   откатываются вместе. Медиа сначала загружается во временный key; после
   commit объект становится доступным по постоянному key. Неиспользованные
   временные объекты удаляются отдельной cleanup-процедурой.
3. Создание или редактирование товара и соответствующая запись `audit_log`
   выполняются на одном соединении и в одной транзакции. Для административных
   команд сохраняется `admin_user_id`, для apply-импорта — системный actor с
   `admin_user_id = NULL` и действием `import`.
4. Заказ и все `order_items` создаются одной транзакцией со снимками названия,
   SKU и цены. Email отправляется только после commit и не откатывает заказ.
5. Изменение статуса заказа и audit-запись фиксируются одной транзакцией.
6. Создание и отзыв серверной сессии — атомарные операции PostgreSQL; наружу
   выдаётся только случайный token, в БД хранится hash.

Сетевые вызовы Tilda, MinIO и email не выполняются внутри открытой
PostgreSQL-транзакции. Повтор внешнего шага должен быть идемпотентным.

## Импорт и dry-run

`npm run catalog:import -- --dry-run` обязателен перед apply и:

- читает и нормализует весь CSV;
- проверяет обязательные поля, конфликты ID/SKU/slug, HTML и изображения;
- формирует детерминированный отчёт и список ручной проверки;
- не пишет PostgreSQL, MinIO и публичные URL;
- завершается ненулевым кодом при ошибке чтения или фатальной структуре CSV.

Apply использует постоянный Tilda UID/External ID, не создаёт дубль при
повторном запуске и сохраняет результат в `import_runs`. Ошибка одного товара
фиксируется в отчёте и не оставляет частично записанную карточку. Публикация
всего набора разрешена только после просмотра dry-run отчёта.

## After-commit revalidation

Revalidation вызывается только после успешного commit. Для изменения товара
инвалидируются:

- `/catalog` и затронутая страница `/catalog/<slug>`;
- `/` для подборок и новинок;
- `/sitemap.xml`;
- страницы затронутых категорий, если они выделены в отдельные маршруты.

При смене slug инвалидируются и старый, и новый URL; стратегия redirect
фиксируется отдельно. Ошибка revalidation не откатывает данные: она логируется
и ставит повторяемую задачу на revalidation. Dry-run ничего не инвалидирует.

## Согласованность и отказы

- Публичная витрина читает только `published`; `draft` и `hidden` отсутствуют в
  каталоге, metadata и sitemap.
- `Quantity` не управляет публикацией или доступностью к заказу.
- Переходы статуса товара заданы явно: `draft -> published`,
  `published -> hidden|draft`, `hidden -> published|draft`; сохранение того же
  статуса разрешено для редактирования полей, а остальные переходы отклоняются.
  При входе в `published` фиксируется `published_at`, при выходе дата очищается;
  каждое изменение обновляет `updated_at`.
- Административные GET требуют действующей сессии, а мутации дополнительно
  требуют CSRF и серверную валидацию.
- Уведомление запускается после сохранения заявки; недоступный email-канал не
  теряет заказ и должен быть виден в журнале повторной отправки.
- Health-check различает отсутствие настройки и недоступность PostgreSQL/MinIO.
- Секреты поступают только через environment Dokploy и не попадают в Git,
  отчёты импорта, логи или клиентский bundle.

## Резервирование

PostgreSQL snapshot и MinIO mirror образуют один backup-комплект с общим
timestamp. Расписание, retention, off-host хранение и процедура восстановления
описаны в `docs/storage-backup.md`.
